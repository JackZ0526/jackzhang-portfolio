checkpoint `ae79547`. One series entry groups GomokuAI and XiangqiAI under
AI & Experiments. It replaces Breakneck Battle Tank in the three homepage

## Contribution and attribution

The user clarified that all implementation code in these AI projects was
produced by coding agents. Their contribution is project direction, experiment
design and UX iteration: defining problems, requesting comparisons, reviewing
agent analyses and playtesting feedback, choosing priorities, and asking for
staged commits and model preservation. The homepage/library role and summary
and the case study introduction state this directly. Technical descriptions
describe the resulting systems; implementation, profiling and benchmark
execution are attributed to the agents rather than to personal code authorship.

## Development history and verification

The case study was revised from the relevant Codex task history, checked against
the current source, configuration and repository documentation. Historical
instructions were treated as evidence, not replayed as commands.

- **分析五子棋AI训练瓶颈**: underused RTX 3090 / i7-14700K, small inference
  batches, unsuccessful multi-game-per-worker experiments and rollback, retained
  multi-leaf MCTS/shared-memory implementation, multiprocess evaluation, visible
  evaluation progress, responsive Web UI and spectator-modal reset fix.
- **优化训练必需部分提速**: profile-led C++ legal-move / attack-detection path,
  a retained Python fallback and staged verification. Suggested future native
  MCTS work is not presented as implemented.
- **分析训练效果不佳原因**: supervised warm-up and evaluation, and the distinction
  between a value-head estimate and calibrated win probability.
- **评估RL棋谱再次预热价值**: playtesting exposed aggressive but shallow play;
  strategic_v2 introduced full 400-MCTS self-play, 500k replay, 10% policy-only SL,
  21-channel history-aware state and migration from validated best iteration 490.
  Later leaf-batch experiments underline why throughput and strength must be
  evaluated separately. No causal strength improvement is inferred solely from
  sequential training runs.

The displayed Gomoku benchmark is explicitly documented in
`F:/Repo/GomokuAI/WINDOWS_RTX3090.md`: iteration 10 vs V1, 8 games × 100 MCTS,
31.01 s threaded vs 12.51 s multiprocess evaluation, approximately 50,245 leaves
and a 4–4 result in both runs. The 2.48× ratio is scoped to that historical local
evaluation, not overall training, general hardware performance or playing strength.
Bars start at zero and use a common scale (12.51 / 31.01 = 40.34%). This update
does not rerun training or GPU benchmarks.

## Training plots

The public CSVs contain only iteration, policy loss, value loss and total loss,
copied directly from the existing local training logs:

| Project | Source run | Rows | Iterations |
|---|---|---:|---|
| GomokuAI | `logs/gui_v2/training.csv` | 100 | 1–100 |
| XiangqiAI | `logs/strategic_v2/training.csv` | 722 | 491–1212 |

The original Xiangqi run starts from a previous checkpoint, not iteration 1.
No rows were dropped, no smoothing was applied, and each plot's y-axis starts
at zero. Both loss heads are shown separately. These are training objectives,
not an independent measure of playing strength. Carried-forward evaluation
values and the internally accumulated strength rating are not plotted as
fresh measurements or public Elo.

`scripts/render-board-ai-charts.py` regenerates desktop/mobile and dark/light
charts from the committed CSVs using matplotlib and Pillow. PNGs are provided
for full-size inspection and WebP versions are used in the page. The whole
snapshot is static and does not load models or call local AI servers from the
published portfolio.

The learning-loop diagram is a semantic HTML ordered list derived from the
documented Self Play → MCTS targets → Replay/Training → Arena promotion loop.
It is an architecture schematic, not a measured trace.
